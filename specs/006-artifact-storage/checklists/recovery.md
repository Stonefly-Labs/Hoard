### RQ-01: Finite Release Versus Non-Cooperative Work

**Status**: Resolved by the maintainer-approved clarification and requirements
re-review on 2026-10-22. Originally a high-priority requirements-consistency
issue, not an observed runtime defect.

**Original finding (before the approved follow-up)**:

- [FR-009 and SC-006](../spec.md#functional-requirements) originally required
  owned resources to be released within documented finite bounds; SC-006
  applied to *all* cancellation, limit and storage-failure cases. US2 scenario 3
  repeated the finite-release promise without a cooperation condition.
- [Finite work and ownership](../contracts/artifact-api.md#finite-work-and-ownership)
  instead limits finite release to cooperative streams, and permits
  non-cooperative stream/native work to retain handles, buffers, slots and
  guards until actual settlement while stopping admission and reporting not-ready.
- [AS-39](../contracts/acceptance.md#required-cases) requires that negative case
  on both providers; the plan and research D6 intentionally reject pretending
  that cancellation can force arbitrary I/O to stop.

**Recommendation approved**: Adopt an explicit requirements
clarification separating finite caller return and cleanup-attempt budgets from
actual resource release. Guarantee finite release for the qualified cooperative
I/O profile. For non-cooperative work, require bounded retained resource counts,
fenced late mutation, explicit incomplete cleanup and blocked admission/readiness
until settlement or owner-controlled process termination. Do not release live
guards, dispose borrowed streams, report successful cleanup or claim rollback.
The alternative is to require a different safely preemptible execution model,
which changes the planned approach and needs its own design assessment.

#### Approved Resolution and Re-review 2026-10-22

The maintainer approved the recommendation: "yeah, let's do what you're
suggesting". The [specification follow-up](../spec.md#approved-follow-up-2026-10-22-rq-01-resource-ownership)
updates exactly US2 scenario 3, FR-009 and SC-006 to express that distinction.

Re-review of CHK012 confirms:

- Caller return and cleanup attempts have finite budgets, while actual release
  is guaranteed within the cleanup bound for the qualified cooperative profile.
- Non-cooperative work retains only bounded owned resources and reports
  incomplete cleanup; admission/readiness remains blocked until settlement or
  owner-controlled process termination. No live guard/handle release, forced
  borrowed-stream disposal or fabricated cleanup/rollback is allowed.
- The unchanged API finite-work/ownership protocol, research D6 and required
  AS-39 specify the same safe outcomes. Exact-ticket uncertainty and exclusion
  survive caller timeout; finite return is not a claim that arbitrary I/O stopped.

CHK012 is satisfied and its marker is checked; recovery is now 20/20 and the
combined custom review is 40/40. AS-39 remains mandatory and unchanged on both
providers. No waiver, runtime proof or new architecture is introduced. The
driver remains `analyze / ready`; this follow-up does not run analysis or
authorize skipping any remaining stage.
